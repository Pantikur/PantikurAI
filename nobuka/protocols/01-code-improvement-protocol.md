## Раздел 2. Протокол рефакторинга

### 2.1 Правила рефакторинга
1. **Одна задача за раз** — не рефакторить и добавлять функционал одновременно
2. **Тесты до и после** — убедиться, что поведение не изменилось
3. **Маленькими шагами** — каждый коммит = одно небольшое изменение
4. **Сохранять API** — публичные интерфейсы остаются совместимыми

### 2.2 Типы рефакторинга
| Тип | Описание | Пример |
|-----|----------|--------|
| Rename | Переименование | Переименовать переменную |
| Extract | Извлечение | Выделить функцию из блока |
| Inline | Встраивание | Заменить функцию вызовом |
| Move | Перемещение | Переместить в другой модуль |
| Simplify | Упрощение | Упростить условие |
| Merge | Объединение | Объединить похожие функции |

### 2.3 Пример протокола
```
Исходный код:
  function process_data(raw) {
    let result = [];
    for (let i = 0; i < raw.length; i++) {
      if (raw[i].active) {
        let val = raw[i].value;
        if (val > 0) {
          result.push(val * 2);
        }
      }
    }
    return result;
  }

Шаг 1: Извлечение фильтра
  function filter_active(raw) {
    return raw.filter(item => item.active);
  }

Шаг 2: Извлечение трансформации
  function double_values(arr) {
    return arr.map(item => item.value > 0 ? item.value * 2 : 0);
  }

Шаг 3: Упрощение
  function process_data(raw) {
    return filter_active(raw).flatMap(item => 
      item.value > 0 ? [item.value * 2] : []
    );
  }
```

## Раздел 3. Протокол исправления багов

### 3.1 Процесс исправления
```
1. 🔍 РЕПРОДУКЦИЯ
   - Создать минимальный пример
   - Записать шаги воспроизведения
   - Создать падающий тест

2. 🔎 ДИАГНОСТИКА
   - Найти корневую причину
   - Определить всеaffected места
   - Проверить на похожие баги

3. 🔧 ИСПРАВЛЕНИЕ
   - Исправить корневую причину
   - Добавить защитные проверки
   - Обновить документацию

4. ✅ ВАЛИДАЦИЯ
   - Запустить репродукционный тест
   - Запустить все регрессионные тесты
   - Проверить на граничных случаях
```

### 3.2 Классификация багов
| Приоритет | Описание | Время реакции |
|-----------|----------|---------------|
| P0 🔴 | Критический: падение системы | Немедленно |
| P1 🟠 | Серьёзный: потеря данных | < 1 час |
| P2 🟡 | Средний: ошибка функционала | < 24 часа |
| P3 🟢 | Незначительный: косметика | < 7 дней |

## Раздел 4. Протокол оптимизации

### 4.1 Принцип: сначала измерить
```python
# ❌ Оптимизация вслепую
def optimize():
    # "Улучшаем" без замеров
    
# ✅ Оптимизация на основе данных
def optimize():
    baseline = measure_performance()  # Замерить до
    change()                           # Применить изменение
    improved = measure_performance()   # Замерить после
    assert improved > baseline         # Убедиться
```

### 4.2 Типы оптимизации
1. **Алгоритмическая** — улучшение сложности (O(n²) → O(n))
2. **Кэширование** — memoization, LRU cache
3. **Параллелизм** — async, multiprocessing
4. **Память** — уменьшение аллокаций, генераторы
5. **I/O** — буферизация, batch-операции

### 4.3 Ограничения оптимизации
- Читаемость > производительность (при приемлемой скорости)
- Оптимизация не должна усложнять код более чем на 20%
- Все оптимизации сопровождаются бенчмарками

## Раздел 5. Протокол депрекейта

### 5.1 Процесс устаревания
```
1. Пометить как @deprecated с указанием замены
2. Добавить warning в runtime
3. Документировать в CHANGELOG
4. Сохранять 2 версии (минимум)
5. Только после — удалить
```

### 5.2 Пример
```python
from warnings import warn
from functools import deprecated

@deprecated("Используйте process_v2() вместо этого")
def process_old(data):
    warn("process_old() устарела, используйте process_v2()", DeprecationWarning)
    return process_v2(data)
```
